Why the boundary sits here
--------------------------

Block header parsing and table construction stay in software: they run
once per block (a few hundred times over the whole file) rather than
once per symbol, so moving them to hardware would add interface
complexity for no measurable gain.

Symbols leave over DMA into a memory buffer, NOT through a
"read next symbol" register. Per-symbol programmed I/O would require
~148,271 Python-level reads per decompression; at even 1 us each that
is ~148 ms, which would consume most of the ~345 ms the accelerator is
meant to save. This is the single most important integration
constraint in the design and it is discussed further in
results/pyflate_accel_analysis.txt.

3. The idea that makes it one cycle
===================================

The software decoder walks a table one entry at a time because it has
to discover the code length by trying lengths in turn. The hardware
does not need to search at all, because pyflate assigns codes
canonically in populate_huffman_symbols: for each length, codes are
consecutive integers starting at first_code[L].

So for a candidate taken from the top L bits of the stream, a
length-L code matches exactly when

    cand - first_code[L] < count[L]

which is one subtraction and one comparison, and the symbol is then at

    base_index[L] + (cand - first_code[L])

in a flat table. No codes are stored and none are compared.

All 20 lengths are tested at once, and the result is unambiguous
because a Huffman code is prefix-free: at most one length can match, so
the arbiter is choosing among mutually exclusive hits rather than
resolving a genuine conflict. The descending priority scan is
belt-and-braces, and it makes the shortest match win if a malformed
table ever produced two.


4. Critical path and frequency
==============================

The longest combinational path runs:

    bit buffer -> peek -> 20 parallel (subtract, compare)
               -> 20-way priority arbiter -> sel_len
               -> 64-bit barrel shift -> bit buffer register

The comparisons are wide but fully parallel, so they contribute one
subtractor delay rather than twenty. The arbiter and the barrel shift
are the two serial elements, and the shift is the more expensive: a
64-bit shift by a 5-bit amount is five mux levels.

A 200 MHz target on a mid-range FPGA is reasonable for this structure.
That is an argument from the path, NOT a synthesis result; nothing here
has been synthesized and no timing report exists.

It also does not matter much. As shown in
results/pyflate_accel_analysis.txt, even at 100 MHz the decoder needs
~1.5 ms per decompression against ~345 ms of remaining software, so the
design is bounded by Amdahl's law and not by its own clock. If timing
closure were a problem, the obvious fix is to retime the barrel shift
into its own stage, costing one cycle of latency and no throughput.
